# OWBastion Test Design Review

Decide whether the affected coverage protects the right claim. A code change does not require a new test, and an existing expectation does not deserve to be kept or updated automatically.

Authority: `.github/docs/testing-policy.md` and `.github/docs/engineering-quality.md`, then the owning repository's `AGENTS.md`. Do not restate them here.

## Questions to answer

- **Claim**: what observable behavior, regression, contract, or stable invariant does the test protect? Without an independent claim, a test records the implementation instead of constraining it.
- **Oracle**: where does the expected value come from? An accepted contract, reviewed evidence, or an established reference counts; output generated by the code under test does not. Hard-coded counts, versions, and inventories are legitimate only when that exact value is the contract.
- **Existing coverage**: what nearby test already protects this, and which distinct plausible failure would this one catch? Duplicates add upkeep without confidence.
- **Stability**: would the assertion survive a correct internal rewrite? Private structure, helper calls, incidental formatting, and mutable inventories are unstable unless a contract exposes them.
- **Layer and cost**: is this the smallest useful layer and input? Fixtures, snapshots, and test-only APIs or visibility changes are maintained code; do not distort production design to expose internals.
- **Ownership**: tests belong to the stable feature they protect, not to an Issue, PR, or task identifier, which may appear only as related history.

Why: a test should fail when behavior is wrong and stay green through a correct refactor. Tests edited only to restore green CI usually fail the first property.

## Decision

Return one recommendation:

- `keep` — protects a durable claim or distinct failure mode at reasonable cost.
- `consolidate` — the coverage is valuable but can be merged or moved to a better surface.
- `rewrite` — the claim is valuable but the assertions, input, or boundary target unstable behavior.
- `delete` — no durable claim or distinct failure mode; it mirrors the implementation.

```text
Recommendation: keep | consolidate | rewrite | delete
Feature: <stable owning feature>
Claim: <behavior, regression, or invariant>
Rationale: <why it does or does not add durable protection>
Existing coverage: <overlap or distinct failure mode>
Cost/coupling: <material concern, if any>
```

Do not manufacture a test because code changed.
