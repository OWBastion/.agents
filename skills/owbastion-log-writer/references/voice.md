# 从现有日志提炼的表达画像

这些是仓库文本中可观察到的表达特征，不是对作者身份的判断。早期开发日志较热闹，近期偏向具体解释；不要将早期宣传句或助手修订后的所有句式都当作作者固定习惯。用户已确认：语气以自然解释为主，允许 emoji 和梗，更多用于开发日志；技术解释应深入浅出，用通俗概念和具体例子让玩家理解。参考近期同类型文章，用户明确指定的样文优先。旧例只用于观察表达，不证明相关功能的当前状态。

## 两类日志共用的句法

| 特征 | 原文短例 | 写新稿时如何用 |
| --- | --- | --- |
| 开发者与玩家面对面 | “各位舍人糕手、钢门信徒” | 使用已有的社区称呼，随话题选择；不强制每次重复完整称呼 |
| 口语动词落到具体操作 | “以前抽随机事件，要先决定这次是增益、减益还是机制” | 写玩家或系统做了什么，少用抽象名词替代动作 |
| 时间对照 | “上一局可能只是在摸索反向路线，下一局就可能直接撞上狂暴之心” | 用前后场景解释变化，不空写“体验更加丰富” |
| 条件和范围前置 | “如果一个 HUD 留在那里，却带着复杂的表达式一直计算，未必比偶尔创建一次更省” | 把成立条件与限制留在句中，不把局部结论写成保证 |
| 直陈原因和选择 | “没有真实数据，现在设计一套漂亮的段位数字意义不大” | 可以坦白暂缓什么，但要说明实际原因 |
| 括号补一小句 | “离开我们很久（？）的「狂暴之心」” | 括号适合轻吐槽、别名或短解释，不堆多层插话 |
| 短句接具体规则 | “阵亡、跳过或特殊挑战能带来有限的额外奖励” | 一句话讲清对象与结果；复杂条件分句说明 |

## 开发日志：解释取舍，也保留社区口吻

- 主语常用“我们”，但重点是玩家遇到的事情：候选池不足、同一局重复提交、倒计时结束后效果没清理。具体例子承担解释，不只是点缀。
- 常见衔接是“过去”“现在”“所以”“不过”“比如”“也就是说”“目前还在……”。它们连接真实的因果、转折和时间关系，不需要每段都放一个。
- 能自然交代限制：有成本、仍需测试、先记数据、以后再定。不要把“计划”抬成“即将彻底解决”。
- 社区语言来自已有玩法，如“钢门信徒”“舍人糕手”“坐牢”“赌本”，或针对具体事件的轻吐槽。笑点贴着实际机制，不另起段子抢走说明。
- 标题通常指出话题或玩家问题，如“事件结束以后，效果也要结束”“地图镜像反转”。长篇可有摘要、预览表和反馈问题，不能据此强制每篇都用同一框架。
- 技术文章可以出现候选池、HUD、循环和算法，但需要用通俗概念和具体例子讲明白。可以深入解释原因与限制，不要求玩家先懂实现；公式或推导需要时保留，并解释它对应怎样的实际行为。

## 更新日志：短、可查、有边界

- 固定对象后直接给变化：“由 A 降低／提高／调整至 B”“不再……”“现在会……”“已移除”。同一条的条件和结果应读在一起。
- 修复句强调错误场景：“修复了玩家解除附身状态后会被传送至地图中心位置的问题”。不替换成“优化传送体验”。
- 引用段承担少量设计理由，条目承担规则和数值；不为每个小改动编理由。
- 事件名、技能名、称号和地图名保留正式叫法。括号用来说明技能键位、AI 或模式范围，不塞内部变量名。
- 更新主题可以有热闹的开头，例如“经典版赌徒回归，手速也是赌本！”，但机制条目仍准确直接。
- Emoji 用于分区识别，加粗用于重要条件与数值。具体排版由当前 Portal 规范决定，不复制历史格式错误。

## 表达强度的取舍

以自然解释组织全文。开发日志允许更多 emoji、社区梗和括号吐槽，更新日志仍以规则和数值为主。技术深度按问题需要展开，用玩家熟悉的概念和具体例子解释，而不是直接展示内部流程清单。

旧文出现过“无限可能”“有史以来最大规模”“绝不留下任何逻辑垃圾”等表述。它们不适合作为自动仿写目标：没有事实支持时，把它们改成具体改变，而不是换另一种宣传词。类似地，历史中的病句、重复、漏标点、失效概率与过度加粗，不属于应模仿的语法特点。

下面是构造的改写示例，用于说明表达选择，不是版本事实或原文引述：

| 笼统写法 | 更贴近样文的写法 |
| --- | --- |
| 优化事件生命周期，提升系统稳定性 | 比如一个事件暂时禁用了技能，倒计时结束后，技能也要恢复。提示消失了，效果却还留着，这个事件就没真正结束。 |
| 本次更新旨在降低挑战门槛 | 完成目标所需的英雄数量由 3 降低至 2。 |
| 全面升级提交系统，提供便捷体验 | 打完保存完整结算截图，一场通关可以同时记录地图进度和挑战结果。 |
